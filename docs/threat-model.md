# Threat model

The asset is the developer's code and credentials. The adversary is anyone who can read what the Bridge sends, including us (the operator of the Expense Tracker API). The Bridge is designed so that even a fully compromised Expense Tracker backend learns nothing about the code.

| # | Threat | Vector | Mitigation | Residual risk |
|---|---|---|---|---|
| 1 | Source code, diffs or file names reach the Expense Tracker API | A bug or a future feature adds a field; the model echoes a path or snippet into the summary | Closed schema (eight fields, unknown keys stripped, strict validation, re-validated in `outbound.ts`); redaction gate on every string (paths, extensions, code fences, backticks, identifier density); held items require explicit approval; guard test that only `outbound.ts` names the endpoints | A functional sentence can still describe a feature in enough detail to hint at architecture. The developer sees every digest before approval only when it is held; clean digests are sent on `send` without a per-item prompt — use `send --dry-run` to read them first |
| 2 | GitHub token leaks | Token written to config or disk; token sent to the wrong host; token printed in logs | Config holds env var names and rejects credential-shaped values; token is read from env only; guard test: `githubToken` never appears in provider or outbound modules; `--dry-run` masks headers; error messages name the variable, not the value | A compromised developer machine or CI runner has the token regardless of the Bridge |
| 3 | Model key leaks | Same vectors as #2 | Same mitigations; the key is sent only to the provider's host; guard test: each provider host is referenced only by its own module | A proxy configured via `provider_base_url` receives the key by the developer's choice |
| 4 | Bridge key leaks and is replayed | Key in logs or repo | Env only; masked in all output; per-project scope and revocation on the server (decisions.md §2); `idempotency-key` makes replays of a captured request harmless duplicates | A stolen key can post bogus digests to that one project until revoked |
| 5 | Secrets inside the PR body or diff are copied into a digest by the model | Model quotes a key from the diff | Secret-shape patterns (AWS, GitHub, Stripe, JWT/Supabase, private keys, Slack, generic 32+ hex/base64) hold the item; prompt forbids credentials | A secret in an unusual format and under 32 characters could pass; review before approving held items, and prefer `send --dry-run` on sensitive repos |
| 6 | Telemetry or a third-party SDK phones home | Dependency or analytics added later | `zod` is the only runtime dependency (tested); every URL literal in `src/` must be on the allow-list (tested); raw `fetch`, no SDKs | A compromised npm package in the dependency tree — mitigated by the tiny tree and lockfile; verify with `npm ls` |
| 7 | The Expense Tracker API reconstructs repo/PR identity | `external_ref` inverted | `external_ref` = first 16 hex of sha256(repo + '#' + pr + merged_at); repo and PR number are never sent; `shipped_at` is day precision | With a known repo name and PR range the hash is brute-forceable in principle (~10⁶ guesses per repo-day). Accepted for v1; a per-project salt is on the roadmap |
| 8 | The model is prompt-injected by PR content | Malicious PR description instructs the model to emit a URL or data | Output must match the structured schema; redaction gate catches URLs, emails, code, identifiers; feedback ids are filtered against server-issued ones | Injection could still shape the functional text (misleading tester instructions). Humans read digests; a bad one is a product bug, not a data leak |
| 9 | A fake Expense Tracker API captures the bridge key and digests | DNS or config pointing at the wrong host | `api_base_url` must be https (except localhost); the host is the developer's explicit configuration; `--dry-run` shows the URL | A developer who misconfigures the host sends digests (not code) to it |
| 10 | Feedback text from the API is used to attack the developer's model or terminal | Hostile feedback item contents | Feedback is data in the prompt, never executed; ids are validated against `^[A-Za-z0-9_-]{1,64}$`; output goes through the schema | Hostile feedback could steer which digest a resolution points at; confidence threshold and human review of resolutions |
| 11 | The Action leaks secrets in logs | `echo`, `set -x`, debug mode | No step prints a secret; the CLI masks credentials; composite action uses `set -euo pipefail` without `-x` | GitHub's own log masking is a second layer, not relied upon |
| 12 | The local queue or cursor is tampered with | Another process edits `.expense-bridge/*.json` | Files are zod-validated on read; a sent item is never overwritten by a re-scan; digests re-validated before send | The queue is trusted local state; protecting the developer's filesystem is out of scope |
| 13 | A held digest is approved carelessly | Approval fatigue | `review` shows the full digest and the masked finding; approvals are recorded with a timestamp; CI never auto-approves | Human judgement; the gate's masking means the reviewer must open the source PR to see the exact string |
| 14 | The Bridge is modified to exfiltrate | Supply chain of the Bridge itself | Apache-2.0 source; guard tests fail the build on any new host or endpoint; small, readable modules; `npm pack` contents listed in `package.json#files` | A malicious published version — verify the tag against the repo, or run from source |

## What this model does not cover

- Compromise of the developer's machine, CI runner or GitHub account.
- The security of the Expense Tracker backend itself (RLS, key hashing, rate limits) — documented in the main repo.
- Legal exposure from a model vendor's data-retention policy; that is the developer's existing relationship with their vendor.
